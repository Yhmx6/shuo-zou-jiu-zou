# 「换一个」距离带改造 · 验收报告

> 任务：替换后的点必须落在「该站的距离带」内，不再破坏「越走越远」的环线形状；
> 带内没有候选时返回人话；不影响「不感兴趣」。基线 HEAD `e91e53c`（M13）。
> 验收时间：2026-10-24 11:25 – 12:20（Asia/Hong_Kong）
>
> **结论：规则 1 个文件落地，验收 1–5 全部通过**（其中第 4 条另附「自然路径」真实点击证据）。

## 1. 改动（只动 `lib/planner.ts`）

| 位置 | 改动 |
| --- | --- |
| `lib/planner.ts` 常量区 | 新增 `SWAP_DISTANCE_BAND_RATIO = 0.9`、`SWAP_BAND_EMPTY_REASON = "这一带没有别的选择，换个时间试试？"`、`DistanceBand` 类型、`distanceBandOf()` / `withinDistanceBand()` |
| `replaceStop` 开头 | 用**换之前**的相邻站到 origin 的直线距离算 `swapBand`；只有 `action === "reroll"` 才有 band，`dislike` 的 `swapBand === null` |
| `replaceStop` 候选池 | `bandAvailable / bandAffordable / bandFallbackAffordable` 三个派生池；**先按距离带过滤，再走原来的打分逻辑**；带内一个候选都没有 → 直接返回指定人话 |
| `replaceStop` 候选取用 | 日落锚点候选、普通替换预筛（24 个）、「换一个」同类目补选（4 个）、「不感兴趣」别类目补选（6 个）、兜底重用池 —— 全部改用带过滤后的池 |

任务书原文口径逐字对上：

```
距离带 = [上一站距离 × 0.9, 下一站距离 ÷ 0.9]
最后一站没有下一站 → 上界无限；第一站没有上一站 → 下界 0
辽阳 0.22 → 0.67 → 1.38 → 2.28（km）实测：
  换第 1 站 [0, 741m]    换第 2 站 [194m, 1533m]
  换第 3 站 [807m, 2534m] 换第 4 站 [2227m, ∞]
```

**与既有规则的兼容性**：`0.9` 与 `buildItinerary` 的距离递增规则（新站 ≥ 上一站 × 0.9）同源。
对任意单调序列，带区间恒非空：下一站 ≥ 上一站 × 0.9 ⇒ 上一站 × 0.9 ≤ 下一站 ÷ 0.9。
所以正常排出来的行程，带里一定有空间，不会因为规则本身「无解」而换不出来。

## 3. 验收 4：带内真换不出来 → 人话，不是报错

先说明一个实测事实：**「一开始带内就没有候选」在现有两座城市的数据上不可达**——
除了上面「带区间对单调序列恒非空」的数学原因，实测 2 城 × 59 份行程 × 199 个站次，
每个环带里都至少有一个候选（最少 1 个：辽阳 08:00 第 1 站 [0, 501m]）。

但这条兜底路径有一条**用户真实可达**的路径（任务书第 5 条允许「不感兴趣」破坏单调）：

```
点 4 次「不感兴趣」后序列：1.55 → 2.65 → 1.49 → 1.97 km（非单调，允许）
第 3 站距离带 = [2388, 2190] ← 区间反转，带内必然没有候选
此时点「换一个」→
  reason: 「这一带没有别的选择，换个时间试试？」
  页面 role=alert 原样显示这句话，行程 4 站仍在，0 条未捕获异常
```

证据（全部真实点击，`build/verify/swap-band-natural-ui.mjs`，截图 `.cache/verify/swap-band-natural-reason.png`）：

```
[PASS] 自然路径：找到区间反转（距离带必然为空）的站 — 第 3 站
[PASS] 自然路径：换一个返回「这一带没有别的选择，换个时间试试？」
[PASS] 自然路径：页面 role=alert 原样显示这句话
[PASS] 自然路径：行程没被清空（失败只提示）
[PASS] 页面没有 console.error / 未捕获异常
```

另外用**受控候选池**直接调真实的 `replaceStop` 验过同一条分支（`build/verify/swap-band-controlled.ts`：
行程用 `/api/plan` 真实结果，候选池只保留带外地点）→ 同样返回这句话。
并单独验证了**页面渲染**（`build/verify/swap-band-ui.mjs` B 组：把 `/api/swap` 响应换成这条失败结果）→
`role=alert` 原样显示、行程不清空、无异常。

「是『没有』还是『系统坏了』」的区分：这句文案只在「候选池非空、但带内一个候选都没有」时出现；
预算不够、都换过了、营业时间/半径不符等各自有更具体的原因（原有逻辑保留未改）。

### ⚠️ 环境问题（与本次改动无关）：高德 JS API 报 `INVALID_USER_DOMAIN`

本机无头 Edge 里地图 SDK 现在加载失败，页面按设计降级成 SVG 示意图。直连高德拿到的原始返回：

```json
{"info":"INVALID_USER_DOMAIN","infocode":"10006","status":"0","key":"（本地 JS Key）","sec_code":"…"}
```

即**这把浏览器端 JS Key 的域名白名单当前不包含本地调试域名**（或白名单配置被改过）——
这是高德控制台的 Key 配置问题，不是代码问题：

- 与本次改动无关：本次只改 `lib/planner.ts` 的 `replaceStop`，地图/排站代码零改动；
- 产品行为正确：SDK 失败 → 自动降级 SVG、页面不崩、console 无 error；
- 受影响的是**依赖地图**的三个旧验收项：`page.mjs` 的「文字导航出现 / 文字导航在地图下方 /
  地图版权 © 2026 AutoNavi」、`map.mjs` 全部（等 `__AMAP_ROUTE_DEBUG__` 超时）、
  `lead-final.mjs` 的换站后动画断言；
- 上一轮（M12/M13）地图可用时这些都已全部 PASS（见 `build/acceptance.md`、`build/road-acceptance.md`）。

**✅ 已修复（2026-10-24 16:2x，用户加了域名白名单后复测）**：这次地图问题确认是域名白名单。
复测时发现一个关键区别——**同一把 Key、同一个页面：**

| 访问地址 | 发给高德的 Referer | 结果 |
| --- | --- | --- |
| `http://localhost:3000` | `http://localhost:3000/` | ❌ `INVALID_USER_DOMAIN`，降级 SVG |
| `http://127.0.0.1:3000` | `http://127.0.0.1:3000/` | ✅ `window.AMap` 正常，地图/路线/文字导航全部渲染 |

所以白名单里加的应该是 `127.0.0.1`。**如果平时用 `http://localhost:3000` 打开页面，地图仍会降级**——
在高德控制台把 `localhost` 也加进白名单即可（或开发时统一用 127.0.0.1）。
验收脚本已改成读 `VERIFY_APP_URL`（默认 `http://127.0.0.1:3000`），复测结果：

## 7. 需要知道的边界

1. **距离带是硬过滤，不是降权**：带内候选一律优先，只有带内一个都没有时才报「这一带没有别的选择」。
2. **带的上界用「换之前」的下一站距离**：换一站不改其它站的位置，所以换完仍在带内；
   连续换同一站时，每次都用当前这一轮的最新邻居距离重算。
3. **「换一个」仍然保留原有的兜底重试**：带内候选在本次会话都换过之后，会允许回到换出过的带内地点
   （避免连点直接卡死）；这不会突破距离带。
4. **「不感兴趣」按任务书第 5 条完全不受带限制**：它可能让序列不再单调，
   之后再对那一段点「换一个」就会看到「这一带没有别的选择」——这是规则叠加的必然结果，文案已说清原因。
5. 本次未改 `/api/swap` 的请求/返回契约、页面、地图；`null` 候选池等边界行为未变。
