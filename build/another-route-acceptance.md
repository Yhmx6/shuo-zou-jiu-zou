# 「再来一条」按钮（整条路线换一条）· 验收报告

> 需求来源：用户问「为什么我找不到整条路线随机的按钮」。
> 排查结论：代码里从来没有这个按钮，而且排程是**确定性**的（同条件每次同一条路线，全项目没有 `Math.random`）；
> 结果页只有逐站「换一个 / 不感兴趣」、改「更多选项」自动重排、切城市、保存卡片。
> 用户选定方案 A：**结果页底部加「再来一条」，带随机种子重排，每次给一条不同但同样合规的路线。**

## 1. 改动（3 个文件）

| 文件 | 改动 |
| --- | --- |
| `lib/planner.ts` | `RouteShape` 加可选 `seed`；新增 `routeJitter(seed, placeId)`（FNV-1a 哈希 → 恒落在 `[0.85, 1]` 的系数）；`pickNext` 打分乘这个系数；`planRounds` / 日落锚点路径把 `constraints.seed` 传下去；`ItineraryConstraints` 加可选 `seed`（zod 上限 2^31-1） |
| `app/api/plan/route.ts` | 请求体加可选 `seed`（int 0–2147483647），透传给 `buildItinerary` |
| `app/page.tsx` | `buildPlanRequestBody` 带 seed；`runPlan` 加 seed 参数并返回 `Itinerary \| null`；新增 `handleAnotherRoute`（随机种子 + 最多 4 次重试）；**站点卡片下面、地图上面**加「再来一条」按钮和「换不出别的组合」的如实提示 |

**首屏不受影响**：按钮只在 `isDone ? 结果区 : 首屏` 的结果区里渲染，未点击前首屏仍然只有「状态文字 + 城市 + 现在就走 + 更多选项」。
「现在就走」不传 seed → 服务端走完全确定性的旧路径（下面有实测）。

## 2. 设计上的三条安全边界

1. **随机系数恒 ≤1**：`pickNext` 的按「打分上界」剪枝仍然成立（真实分 ≤ 未乘的上界），不会漏掉真正的赢家。
2. **只改「在合规候选里选谁」**：所有过滤（营业时间 / 半径 / 预算 / 已去过 / 用餐时段 / 距离递增 / 800m 去重）都在打分之前，种子碰不到它们。
3. **不用 `Math.random` 排程**：种子 → 哈希 → 系数是纯函数，**同一个 seed 永远同一条路线**（可复现、可测）。

页面侧两个兜底：
- 组合很少的场景，排出来可能和当前一样 → 换种子重试，最多 4 次；4 次都一样显示「这一带这个时段可选的地方有限，暂时换不出别的组合了」；
- 偶发排不出来（例如某站到终点算不出返程路线）→ 也换种子重试，全部失败才显示原因，旧行程不清空。

## 3. 验收：API 矩阵（`node build/verify/random-route.mjs` → PASS）

5 个场景 × 10 个种子，逐条复算规则（距离单调 ≤10% 回退 / 同类目 800m / 第 3 站起不落回前序 800m / 预算 / 覆盖正餐必须有餐厅 / segments = stops+1）：

| 场景 | 不给 seed | 同 seed 可复现 | 10 个 seed 换出 | 规则 |
| --- | --- | --- | --- | --- |
| 辽阳 09:00 | 确定 ✓ | ✓ | **6 种**（分布 [5,1,1,1,1,1]） | 全合规 |
| 辽阳 15:20 | 确定 ✓ | ✓ | **8 种**（[2,2,1,1,1,1,1,1]） | 全合规 |
| 杭州 11:00 | 确定 ✓ | ✓ | **7 种**（[2,2,2,1,1,1,1]） | 全合规 |
| 杭州 17:00 | 确定 ✓ | ✓ | **6 种**（[3,2,2,1,1,1]） | 全合规 |
| 杭州 15:20 | 确定 ✓ | ✓ | 2 种（[5,5]，该时段可排候选少） | 全合规 |

- 「不给 seed 两次结果完全一样」= 首屏「现在就走」没有变随机，既有验收不受影响。
- 「同一 seed 两次一样」= 可复现，测试不会 flaky。
- 第 1 站：非饭点场景对所有 seed 都不变（仍是「最近的合规点」硬规则）；杭州 17:00 出现 2 种，
  原因是第 1 轮是强制用餐轮，种子影响「这一轮装不装得进预算」，装不进就回退全类目池（既有兜底逻辑），
  两个池各自取最近的合规点 —— 与上一轮验收不冲突，已写进脚本注释。

## 6. 需要知道的边界

1. **「再来一条」变的是第 2 站及以后**：第 1 站仍由上一轮的硬规则决定（最近的合规点），
   所以整条线的前三公里可能看起来一样 —— 这是刻意保留的验收约束，不随种子变。
2. **组合数取决于城市和时间**：辽阳/杭州多数时段 6–8 种；杭州 15:20 只有 2 种（能进正餐时段、
   营业时间已知的候选太少）。这时按钮会重试到换出另一条，4 次都换不出才提示。
3. **每次重排还会重新生成 LLM 文案**（`/api/plan` 现有逻辑），所以文案也会跟着变；比纯换站慢一点（约 0.5–2s/次）。
4. 换站历史（`换一个` 的记录）在「再来一条」成功后清空（新路线 = 新会话），与「改更多选项重排」同口径。
5. 偶发排不出来会重试；4 次都失败才显示原因，旧行程保留不清空。
